# Workflow & reporting — status.json, TECHNICAL_DEBT, hotspots, resume, dashboard

The mechanics behind app-audit's "Resuming an interrupted round", Step 2.1
(hotspots), Step 5.6 (standing artifacts), audit-fix Step 5.3, and
pre-commit-verification's reliability tracking. The shared idea: the audit's
state and results are **data on disk with stable shapes** — so a crash loses
nothing, CI needs no markdown parsing, and "what are we living with?" has a
one-glance answer.

The `.audit/` file inventory after G7:

| File | Written by | Volatility | Purpose |
|---|---|---|---|
| `run_state.json` | app-audit, continuously | volatile | live progress; resume checkpoint |
| `status.json` | app-audit 5.6 / audit-fix 5.3 | per round | stable contract for CI/tools/dashboard |
| `check-history.json` | pre-commit-verification | per run | reliability (pass³) tracking |
| `dashboard.html` | app-audit 5.6 (opt-in) | per round | human view of status.json |
| `TECHNICAL_DEBT.md` (repo root) | app-audit 5.6 / audit-fix 5.3 | per round | accepted-debt ledger |

## §1 — `.audit/status.json` schema (`greenloop-status/1`)

```json
{
  "schema": "greenloop-status/1",
  "repo": "<origin URL or directory name>",
  "updated": "<UTC ISO-8601>",
  "round": 5,
  "head": "<SHA at round close>",
  "scope": {"categories": [1, 3, 5], "change_scope": "whole|diff|recent|pr",
            "ref": "<PR # / branch / null>"},
  "findings": {
    "open":      {"critical": 0, "high": 2, "medium": 4, "low": 3, "info": 1},
    "fixed":     {"critical": 1, "high": 3, "medium": 2, "low": 0, "info": 0},
    "deferred":  {"critical": 0, "high": 0, "medium": 2, "low": 2, "info": 0},
    "dismissed": {"critical": 0, "high": 0, "medium": 1, "low": 0, "info": 0}
  },
  "coverage": {"items_covered": 27, "items_total": 27, "could_not_verify": 2},
  "verification": {"clean_room": "pass|fail|not-run",
                   "witness": ".audit/witness/<ts>.json or null",
                   "truth_scores": {"min": 0.90, "median": 0.93, "max": 1.0}},
  "learning": {"learned_rules": 2, "chronicle_lessons": 6, "cleared_registry": 4},
  "history": [
    {"round": 4, "date": "2026-05-30", "opened": 14, "fixed": 11,
     "deferred": 2, "dismissed": 1,
     "fix_pass": {"fixed": 11, "deferred": 1, "reverted": 1,
                  "truth_median": 0.93, "clean_room": "pass"}}
  ],
  "metrics": {"wall_clock_min": 38, "execution_mode": "parallel",
              "reviewers": 7, "challenged": 41, "refuted": 6,
              "tokens": null}
}
```

Optional field for the dashboard's findings board (omit for count-only output).
The first six keys drive the Kanban card; the trailing optional keys
(`description`, `evidence`, `snippet`, `suggested_fix`, `suppression`) power the
dashboard's **drill-in drawer** — include them and a click on the card shows the
full finding without leaving the page. `status` may be any of
`open|fixed|deferred|dismissed|suppressed` (suppressed findings, written by
`greenloop-suppress.py`, render in their own column dimmed, never dropped):

```json
  "findings_list": [
    {"id": "3.2", "severity": "high", "status": "open", "category": 3,
     "title": "OAuth token in error log", "location": "auth/refresh.ts:88",
     "confidence": 0.85, "provenance": "new",
     "class": "secret-in-log",
     "description": "Refresh token written to the error log on failure.",
     "evidence": ["semgrep secret-in-log", "blind challenge: CONFIRMED"],
     "snippet": "log.error(`refresh failed: ${token}`)",
     "suggested_fix": "Log the token's last 4 chars only, or omit it.",
     "suppression": null}
  ]
```

Rules:
- `history` is append-only, one entry per round — it IS the timeline. Trend
  tooling reads it directly; nothing parses AUDIT_LOG.md.
- Update **counts in place** for the current round; never rewrite history.
- `tokens: null` means the host didn't expose spend. Never estimate into this
  field — a wrong number in a machine-readable file gets believed.
- CI gate example: `jq -e '.findings.open.critical == 0 and .findings.open.high == 0' .audit/status.json`

## §2 — `TECHNICAL_DEBT.md` format

```markdown
# Technical debt — accepted, on the record
<!-- regenerated by greenloop each round from AUDIT_LOG deferred findings -->
<!-- this file answers: "what are we knowingly living with, and since when?" -->

## ⚠ Aged debt (3+ rounds — re-decide or dismiss explicitly)
- [High] core/event_bus.rs:55 — event ordering not guaranteed
  deferred round 2 ("too risky pre-launch"), now 4 rounds old

## Category 4 — Error handling
- [Medium] workers/retry.rs:31 — backoff cap missing
  deferred round 5: "vendor SDK rewrite planned Q3"

## Category 9 — Test coverage
- [Low] api/export.rs — no test importers
  deferred round 4: "feature behind flag, not GA"
```

Rules: **deferred findings only** (open = work in flight; dismissed = decided
not-debt). Regenerate wholesale from AUDIT_LOG every round — never hand-edit
(it would diverge from the log, and the log wins). Age = current round minus
the round the finding was first deferred. The aged-debt section exists because
"deferred" silently becoming "forever" is the failure mode of every debt list.

## §3 — Churn × coverage hotspots (Step 2.1)

```bash
# churn: commits touching each file in the last 6 months
git log --since=6.months --name-only --pretty=format: -- . \
  | grep -v '^$' | sort | uniq -c | sort -rn | head -30
```

Cross with the coverage signal already on hand — no coverage tool required:
- acceptance-map rows marked `UNMAPPED` → the file's promises have no test;
- codemap `imported_by` containing no test files → nothing exercises it;
- (when a real coverage report exists in the repo, use it instead.)

Score = churn rank × coverage gap. Take the top 3–7 as the round's
**hotspots**: name them in the scope proposal, review them first within each
category (Phase 3), and mark them in the coverage declaration. Skip the
computation entirely for PR/diff-scoped rounds — the change-set already IS the
priority. Exclude generated/vendored paths (the codemap's tags know them).

## §4 — Resume protocol (crash recovery)

`run_state.json` must always contain enough to restart: current phase, locked
scope, per-category item cursor, findings so far (full text, not references),
detector results, and the round's start HEAD. The audit updates it at every
phase transition and every ~5 checklist items — cheap insurance, paid
continuously.

On resume:
1. Read `run_state.json`; present the checkpoint ("category 3, item 7/12,
   9 findings so far") and get a yes.
2. **HEAD unchanged** since checkpoint → re-raise `.audit/.audit-active`
   (if hooks are installed) and continue the Phase 3 loop at the cursor.
3. **HEAD moved** → re-run the Phase 0 pre-commit gate, refresh cartographer
   incrementally, then continue. Completed categories stay completed, but the
   log notes: "files changed mid-round: <list> — reviewed pre-change; consider
   them for the next round." Findings already made are kept (they cite the SHA
   they were found at).
4. Never re-derive findings already in the checkpoint, and never re-ask scope
   approval — the scope was locked in Step 2.3.

audit-fix recovery is simpler (see its "Crash recovery" section): the plan,
baseline, and per-fix commits are all on disk; resume = first finding that is
neither fixed nor deferred, after reverting any half-applied fix the dead
session left in the tree.

## §5 — Run metrics (honest accounting)

Record per round, in AUDIT_LOG + `status.json.metrics`:

- wall-clock total and per phase (coarse is fine — minutes, not ms),
- execution mode + reviewers dispatched (sequential | parallel × N),
- detector runtimes and which were skipped (not installed),
- challenge stats (challenged / confirmed / refuted / weakened / registry hits),
- token/cost **only if the host exposes it** — else `null` + "not exposed".

Purpose: the user deciding "was parallel mode worth it?" or "can we afford
whole-codebase rounds weekly?" needs real numbers, not vibes. Never let
metrics gatekeep quality steps (e.g., skipping the challenge to save time is
not an optimization, it's a different product).

## §6 — Dashboard generation (Step 5.6, opt-in)

`references/dashboard-template.html` is self-contained: inline CSS + JS, no
server, no CDN, no network, works from `file://`. Generation is one
substitution — replace the line

```js
window.AUDIT_DATA = {/*GREENLOOP_DATA*/};
```

with `window.AUDIT_DATA = <contents of status.json>;` and write the result to
`.audit/dashboard.html`. (Python one-liner or careful sed; the marker appears
exactly once.) It renders a **findings workbench**, not just a scoreboard:

- a **Kanban board** across Open / Fixed / Deferred / Dismissed / **Suppressed**
  (the suppressed column appears only when suppressions exist; cards dimmed);
- when `findings_list` is present, **search + severity-chip filters** above the
  board, and a **drill-in drawer** — clicking a card opens its description,
  evidence, code snippet, suggested fix, and suppression reason (whatever
  `findings_list` carries; graceful when fields are absent);
- a per-round **trend strip** from `history`, coverage + verification summary
  cards, and the metrics line.

Styled to the **technical-minimal** system in `ui/design-system.md` (one green
accent + a five-step severity ramp, monospace data, system-sans chrome).
Dark/light follows the OS via `prefers-color-scheme`; motion is disabled under
`prefers-reduced-motion`.

The dashboard is a **view**, never a store: regenerate it from status.json
each round; hand-edits are overwritten by design. If the template and schema
ever disagree, the schema wins — bump `greenloop-status/N` and update the
template, not the other way around.
